## Why this matters

`/add` is unauthenticated and ungated. Measured against a local instance of this
Worker: 40 links created from a single client in 1.5 seconds, with no captcha,
no auth, and no throttle. A spammer can fill the database at the speed of their
network connection, and every link they create is a `mjr.sh` URL that inherits
the domain's reputation.

Rate limiting is also a prerequisite for the blocklist work (plans 003/004):
without it, an attacker can simply retry submissions until one slips past a
reputation check.

After this plan, a single client IP can create at most 5 links per minute, and
the rest receive `429`.

`src/index.ts` in full as it exists today:

```ts
import { add } from "./handlers/add";
import { edit } from "./handlers/edit";
import { redirect } from "./handlers/redirect";
import { globalStats, keyStats } from "./handlers/stats";
import { keyValidator } from "./utils";

const notFound = () => Response.json({ error: "Not found" }, { status: 404 });

export default {
	async fetch(request, env) {
		const { pathname } = new URL(request.url);
		const [first, second, ...rest] = pathname.split("/").filter(Boolean);

		if (rest.length > 0) return notFound();

		if (first === undefined) return notFound();
		if (first === "add" && second === undefined) return add(request, env);
		if (first === "stats" && second === undefined)
			return globalStats(request, env);

		const key = keyValidator.safeParse(first);
		if (!key.success) return Response.json(key.error, { status: 400 });

		switch (second) {
			case undefined:
				return redirect(env, key.data);
			case "edit":
				return edit(request, env, key.data);
			case "stats":
				return keyStats(request, env, key.data);
			default:
				return notFound();
		}
	},
} satisfies ExportedHandler<Env>;
```

Repo conventions to match:

- Tabs, double quotes, semicolons — Biome enforces; run `bun run check`.
- `Env` is an ambient global generated by `wrangler types` into
  `worker-configuration.d.ts`. Never `import type { Env }`. After changing
  bindings in `wrangler.toml` you must re-run `bun run types` so `Env` gains the
  new binding.
- Error responses are produced with `Response.json({ error: "…" }, { status: N })` —
  see `notFound()` above. Match that shape.

Verified facts about the rate-limiting binding (tested with wrangler 4.129/4.131
in this environment, not assumed):

- The `[[ratelimits]]` TOML block is accepted and produces a binding named in
  `wrangler deploy --dry-run` output as `env.NAME (5 requests/60s)  Rate Limit`.
- `period` **must** be exactly `10` or `60`. No other value is accepted.
- The call is `await env.NAME.limit({ key: string })` returning `{ success: boolean }`.
- It works in `wrangler dev` locally (mode shows `local`), and enforcement was
  observed: with `limit = 5, period = 60`, eight sequential calls returned
  `200 200 200 200 200 429 429 429`.
- Docs: https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/

## Steps

### Step 1: Declare the rate-limiting binding in `wrangler.toml`

Add this block. Put it after the `[[routes]]` block and before `[assets]` so
related bindings stay grouped near the bottom of the file:

```toml
[[ratelimits]]
name = "ADD_LIMITER"
namespace_id = "1001"
simple = { limit = 5, period = 60 }
```

`namespace_id` is an arbitrary account-unique string identifier; `"1001"` is
fine. `period` must be `10` or `60` — use `60`.

**Verify**: `bunx wrangler deploy --dry-run --outdir /tmp/mjr-dryrun` → exit 0,
and the binding table in the output contains a line like
`env.ADD_LIMITER (5 requests/60s)   Rate Limit`.

### Step 2: Regenerate the ambient `Env` type

```sh
bun run types
```

**Verify**: `grep -n "ADD_LIMITER" worker-configuration.d.ts` → returns a match
showing `ADD_LIMITER: RateLimit;`.

If it does not appear, STOP — the binding is misconfigured and step 3 will not
typecheck.

### Step 3: Enforce the limit on `/add` in `src/index.ts`

Modify only the `/add` branch of the router. The current line is:

```ts
		if (first === "add" && second === undefined) return add(request, env);
```

Replace it with a version that checks the limiter first, keyed on the client IP.
Cloudflare provides the client IP in the `CF-Connecting-IP` request header. Fall
back to a constant when the header is absent (it is absent in some local dev
scenarios) so the code never keys on `undefined`.

The shape to produce:

```ts
		if (first === "add" && second === undefined) {
			const clientIp = request.headers.get("CF-Connecting-IP") ?? "unknown";
			const { success } = await env.ADD_LIMITER.limit({ key: clientIp });
			if (!success) {
				return Response.json(
					{ error: "Too many requests" },
					{ status: 429 },
				);
			}
			return add(request, env);
		}
```

Do not restructure the rest of the router. Do not add the check to any other
branch.

**Verify**: `bun run typecheck` → exit 0, no output. Then `bun run check` → exit 0.

### Step 4: Smoke test the limit against a local Worker

Set up local state (safe: `--local` only touches `.wrangler/state`):

```sh
cp -n .dev.vars.example .dev.vars || true
bun run build
bunx wrangler d1 execute mjr-sh --local --file=./schema.sql -y
bunx wrangler d1 migrations apply mjr-sh --local
bunx wrangler dev --port 8799 > /tmp/mjr-002.log 2>&1 &
for i in $(seq 1 30); do curl -sf -o /dev/null http://127.0.0.1:8799/stats && break; sleep 1; done
```

Run the test:

```sh
B=http://127.0.0.1:8799
echo "8 creates against limit=5/60s:"
for i in $(seq 1 8); do
  printf "%s " "$(curl -s -o /dev/null -w '%{http_code}' "$B/add?url=https://example$i.com")"
done; echo

echo "reads must still work (expect 200):"
curl -s -o /dev/null -w '%{http_code}\n' "$B/stats?nocache=$RANDOM"
```

Stop the dev server: `pkill -f "wrangler dev"`.

**Verify**: the first five creates print `200`, the remaining three print `429`.
The `/stats` read prints `200` — proving read paths are unaffected.

## Maintenance notes

- `limit = 5, period = 60` is a deliberate starting point for a low-traffic
  community service. If legitimate users hit it, raise `limit`; `period` can
  only ever be `10` or `60`.
- The limiter keys on `CF-Connecting-IP`, so it is per-IP. A distributed
  submitter across many IPs is not stopped by this — that is what the blocklist
  plans (003/004) address. These are complementary, not redundant.
- The `"unknown"` fallback key means all header-less requests share one bucket.
  In production Cloudflare always sets `CF-Connecting-IP`, so this only affects
  local dev.
- A reviewer should confirm no read path gained a limiter call — redirect
  latency and cacheability matter more than write-path strictness here.
- Deliberately deferred: a zone-level WAF rate limiting rule (free plan allows
  one rule per zone) would add defense in depth without code. Worth doing in the
  dashboard, but it is configuration, not a code change, so it is not in this plan.
